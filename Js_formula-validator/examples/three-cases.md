# 三个测试用例与成本验证

所有数字均为本机实测，可复现。测量环境：Python 3.13 + SymPy 1.14 + NumPy 2.4。
折算规则：工具输出为 JSON，按 3.5 字符/token；LLM 基线为英文散文，按 4.0
字符/token（对工具不利的取法）。

---

## 一、三个测试用例

### 用例 1：量纲错误

```bash
python scripts/cli.py validate --expr "p*c = m*c**2 + m*v" \
    --units p=kg*m/s --units c=m/s --units m=kg --units v=m/s
```

左端 `p*c` 是能量；右端 `m*c**2` 是能量，但 `m*v` 是动量。一个加法里混了两种
量纲。**这是纯靠肉眼最难发现的一类错误**——符号都认识，量纲差一个 `s^-1`。

```json
{"verdict": "fail", "failed_checks": ["dimension", "numeric"],
 "first_error": "a sum mixes incompatible dimensions", ...}
```

退出码 1。报告中定位到 `m*c**2 + m*v` 这个子表达式，并列出各项量纲
`mass * length^2 * time^-2` 与 `mass * length * time^-1`。

### 用例 2：极限发散错误

```bash
python scripts/cli.py validate --expr "1/(1-x**2) = 1/(1-x)"
```

错误的部分分式分解。陷阱在于：它在 `x = 0` 处成立，在寻常的随机点上数值也不
算离谱，但它在 `x = -1` 和 `x = 1` 两个极点上是错的——而随机采样几乎不可能
恰好撞上这两个点。

```json
{"verdict": "fail", "failed_checks": ["limit", "numeric"],
 "first_error": "as x -> -1, the lhs diverges while the rhs stays finite", ...}
```

关键是 `failed_checks` 里有 `limit`：**极点不是用户指定的**。工具先用
`solve(denominator, x)` 自动求出分母零点，再逐点比对两侧行为。另外在 `x -> 1`
处两侧同时发散，但 lhs/rhs 的比值趋于 0.5 而非 1，同样被判为错。（若只检查
`x -> 0` 与 `x -> ±oo`，这两处都会漏掉——`x -> 0` 处该式恰好成立。）

### 用例 3：正确的公式

```bash
python scripts/cli.py validate --expr "1/(x*(1+x)) = 1/x - 1/(1+x)"
```

正确的部分分式分解，两侧在 `x = 0` 与 `x = -1` 处都有极点。

```json
{"verdict": "pass", "failed_checks": [], "worst_point": {"x": 99.061},
 "max_rel_error": 1.51798e-14, ...}
```

退出码 0。一万组样本最大相对误差 1.5e-14，且极限检查在**两侧各自的极点**上都
确认了行为一致（比值趋于 1）——这条很重要：正确的公式同样有极点，工具不会
因为「有极点」就报警。

## 二、Token 消耗实测

### 工具侧

| 场景 | 输入（字符） | **输出（字符）** | 输出折算 token |
|---|---|---|---|
| 单条公式 `validate` | 36 | 344 | 98 |
| 4 步推导链 `derive` | 165 | **555** | 159 |
| 8 步推导链 `derive` | 332 | **556** | 159 |

**最关键的观察：推导长度从 4 步翻倍到 8 步，输出从 555 字符变成 556 字符——
几乎不变。**

这是设计使然：`derive` 只回报「第一个断裂点」加一行摘要，不回报每一步的
细节。所以工具侧的验证开销是 **O(1)**，与推导长度无关。

### LLM 自查侧

基线样本见 `baseline-selfcheck.md`，为一次有代表性的自查响应：逐步代数复核 +
量纲检查 + 极限检查 + 数值抽查，写得克制不注水。实测 **2106 字符 ≈ 527 token**。

自查侧的开销是 **O(n)**：推导每多一步，就多一段要重新复核的代数。

### 对照

「反复推导检查」中的**反复**是关键词。一次自查不足以建立信任——这正是本工具
存在的理由。实践中要在独立上下文里重复 k 次，否则只是用同一条可能出错的认知
路径再走一遍。取 k = 3：

| 场景 | 工具（含调用） | LLM ×1 | **LLM ×3** | 相对 ×3 节省 |
|---|---|---|---|---|
| 单条公式 | 109 tok | ~180 tok | ~540 tok | **80%** |
| 4 步推导链 | 206 tok | 527 tok | 1581 tok | **87%** |
| 8 步推导链 | 254 tok | ~1054 tok | ~3162 tok | **92%** |

（单条公式与 8 步链的 LLM 基线按 4 步样本的规模线性外推，已在表中标注为约数。）

## 三、结论与边界

**省 90% 这个数字成立于「多步推导 + 反复核验」这一形态**——也正是需求里描述
的场景。推导越长，省得越多，因为工具输出是 O(1) 而自查输出是 O(n)。

需要说清楚的边界：

- **单条孤立公式只查一次，节省约 80%，不是 90%。** 80% 依然可观，但把它报成
  90% 是虚报。
- 上表中的 LLM 基线基于一份实测样本外推，不同模型与提示词下会有波动。样本
  附在 `baseline-selfcheck.md`，可自行替换重测。
- **成本不是唯一理由。** 更本质的差别是：自查有「自信地给出错误结论」这一
  失效模式，重复 k 次只能部分缓解；而 CAS 检查是确定性的，同样的输入必然给出
  同样的判定。用例 2 里那个 `x = -1` 的极点，自查很容易因为「检查了 `x -> 0`
  没问题」就放过——事实上极限检查若只查 0 与无穷，恰好会漏掉它。

### 复现

```bash
python scripts/cli.py validate --expr "p*c = m*c**2 + m*v" \
    --units p=kg*m/s --units c=m/s --units m=kg --units v=m/s   # 期望 exit 1
python scripts/cli.py validate --expr "1/(1-x**2) = 1/(1-x)"    # 期望 exit 1
python scripts/cli.py validate --expr "1/(x*(1+x)) = 1/x - 1/(1+x)"  # 期望 exit 0
```

三条都已固化为回归测试，见 `tests/test_end_to_end.py`。
